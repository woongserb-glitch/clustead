- **무엇이 문제인지:** JSON 파싱 성공과 객체 타입을 동일하게 취급하여 곧바로 `payload.get()`을 호출한다.

- **고치는 방향:** 본문 크기와 객체 타입을 먼저 검증하고, 허용하는 `key` 문자열만 받는다. 잘못된 본문은 400 또는 정책에 맞는 무시 응답으로 처리한다.
- **확신 정도:** **확인함** — 격리 HTTP 재현. 앱 전체 적재·네트워크·분석 DB 쓰기 없이 수행.

- **터지는 상황 / 근거:** 예를 들어 지하철 CSV 누락 시 `services/preload_service.py:698–704`가 예외를 삼킨다. 점수 인덱스는 빈 소스를 건너뛰고 완성된다(`services/ranking_service.py:85–116`). 단지 CSV만 읽혔다면 `app.py:416–417`은 200을 반환한다. Explore의 지하철 조건은 빈 baseline에서 결과가 없게 되고, 정상 결과 없음과 데이터 적재 실패를 구분하지 못한다. 실제 파일을 지우지 않고 확인한 코드 경로다.
- **고치는 방향:** 필수 데이터별 적재 성공·행 수·필수 컬럼·버전 일치 여부를 readiness 상태에 반영한다. 필수 파일 실패 시 준비되지 않음을 알리고, 선택적 자료 실패는 해당 기능의 데이터 불가 상태로 구분한다.
- **확신 정도:** **확인함** — 오류 처리와 healthz 조건 확인. 별도 프로세스의 지하철 baseline 목록을 메모리에서만 비우고 `/healthz` **200**을 재현한 뒤 복원했다. 실제 파일·서버의 누락 여부는 조사하지 않음.

## 8. IP 신뢰 경계와 워커별 rate limit

- **무엇이 문제인지:** `real_client_ip()`는 요청 출처와 `TRUST_PROXY` 설정에 관계없이 `CF-Connecting-IP`를 최우선으로 신뢰한다. 원본 nginx에 직접 도달할 수 있다면 이 헤더를 바꾸어 IP별 제한을 피할 수 있다. 별도로 기본 `memory://` 카운터는 워커 사이에서 공유되지 않아, 워커 2개 구성에서 명목상 30회/분이 서비스 전체 30회/분을 보장하지 않는다.
- **터지는 상황 / 근거:** `app.py:153–155,163–168`, `docker-compose.app-only.yml:13`의 2워커 설정. 저장된 host nginx 설정은 프록시 헤더를 설정하지만 CF 헤더를 신뢰 출처에서만 받게 정제하는 규칙은 보이지 않는다(`deploy/nginx/clustead-host.conf:81–96`). 이 파일 밖의 방화벽·nginx 공통 설정·Cloudflare 정책은 확인하지 않았으므로 **현재 외부에서 실제 우회 가능하다는 결론은 추정**이다. 특정 봇 UA에만 적용되는 nginx 제한(`26–32,71–73`)은 일반 요청의 대체 제한이 아니다.
- **고치는 방향:** 신뢰하는 Cloudflare/프록시 출처에서 확인한 IP만 제한 키로 사용하고 직접 연결의 전달 헤더는 제거한다. 서비스 전체 제한이 필요한 경로는 프록시 또는 공유 저장소에서 집계한다. 961MB 환경에서는 공유 저장소 추가 비용도 함께 고려한다.
- **확신 정도:** 헤더 신뢰·워커별 기본 설정은 **확인함**. 운영 원본 접근 가능성과 실제 제한 배수는 **추정**(서버·환경 설정 미열람).

## 9. 관리자 인증 토큰을 URL과 로그에 보존

- **무엇이 문제인지:** 쿼리 `admin_token`으로 인증하고 템플릿이 관리자 링크·격자 API URL에 이를 계속 붙인다. 요청 진단은 쿼리 전체를 저장·출력하므로 인증 비밀이 진단 로그에 남는다.
- **터지는 상황 / 근거:** 관리자 접속 `?admin_token=...` 후 느린 요청이 기본 5초를 넘으면 `app.py:381`의 `request.full_path`가 그대로 출력된다. 모든 요청의 전체 경로도 `app.py:367` → `services/request_tracker.py:21–30`에 들어가 워커 중단 로그에서 사용된다(`gunicorn.conf.py`의 `worker_abort`). `templates/admin_grid.html:265`는 API 호출마다 토큰을 쿼리에 덧붙인다. 로그에서 토큰 값을 수집하거나 실제 비밀을 확인하지 않았다.
- **고치는 방향:** 인증 전달은 헤더 또는 보호된 세션으로 통일하고, 요청 URL을 기록하기 전에 인증 쿼리를 제거한다. 관리자 응답에는 명시적인 `private, no-store` 정책을 둔다.
- **확신 정도:** **확인함** — 인증 입력·URL 생성·로그 출력의 연결 확인. 실제 서버 로그에 토큰이 있었는지는 미확인.

## 10. 공유 JSON의 잘못된 Unicode가 Explore를 500으로 만듦

- **무엇이 문제인지:** 공유 쿼리의 Base64/JSON 해석은 예외를 처리하지만 JSON 문자열 안의 단독 surrogate는 통과한다. 다시 공유 URL을 만들면서 UTF-8로 인코딩할 때 예외가 난다.
- **터지는 상황 / 근거:** **`GET /explore?q=eyJndSI6Ilx1ZDgwMCJ9` → 500**을 실제 Flask test client에서 재현했다. Base64 내용은 `{"gu":"\ud800"}`이며, `json.loads`는 이 문자열을 허용한다(`app.py:7352`). `normalize_explore_filters()`도 문자를 보존하고, `json.dumps(..., ensure_ascii=False).encode("utf-8")`(`7462`)에서 `UnicodeEncodeError`가 발생한다. 일반적인 깨진 `%FF%FE` 쿼리는 안전하게 무시되므로 구분해야 한다.
- **고치는 방향:** 공유 payload의 텍스트 값에 유효한 Unicode·길이 검증을 적용하고, 공유 URL 재생성의 실패도 입력 오류로 처리한다. 유효하지 않은 문자를 거부하거나 일관되게 치환한다.
- **확신 정도:** **확인함** — 원본 라우트에서 500 재현. 네트워크·파일 쓰기 없이 실행.

## 11. 관리자 격자 좌표가 유한수·지리 범위인지 검사하지 않음

- **무엇이 문제인지:** bbox는 `float()` 성공과 최소/최대 순서만 검사한다. NaN은 크기 비교를 통과하며, 무한대·초대형 유한값도 뒤의 정수 변환/SQLite 바인딩을 실패시킨다.
- **터지는 상황 / 근거:** 가짜 관리자 토큰으로 로컬 `/admin/grid/cells?layer=cctv&bbox=...` 요청을 인증하고, `nan,127,38,128`, `-inf,127,38,128`, `1e100,127,1e101,128` 모두 **500**을 확인했다. `services/grid_service.py:240–244`의 정수 셀 변환과 후속 조회까지 예외가 전파된다. 인증 없는 동일 관리자 경로는 404였다.
- **고치는 방향:** 네 값의 유한성, 위·경도 허용 범위, 최대 조회 영역을 경계에서 검사하고 잘못된 bbox는 400으로 반환한다.
- **확신 정도:** **확인함** — 로컬 원본 라우트 재현. 관리자만 접근하는 범위여서 낮음으로 분류.

## 12. baseline.db 누락 시 RAM 전제가 바뀌는 자동 폴백

- **무엇이 문제인지:** SQLite 사용 여부를 파일 존재 여부만으로 정한다. 파일이 없으면 academy·medical 등 11개 baseline을 Python 목록·dict로 적재하는 방식으로 자동 전환한다. 961MB 호스트/768MB 컨테이너 상한에 맞춘 SQLite 전제가 깨지는 상황을 정상 호환 폴백으로 처리한다.
- **터지는 상황 / 근거:** `services/preload_service.py:204,281–300`과 각 `load_*_baseline_data()`의 `_USE_SQLITE_BASELINE` 분기. 해당 11개 CSV의 현재 디스크 크기 합계는 **416,858,699 bytes**이다(academy 135,409,472, medical 194,740,770 bytes 포함). 이는 힙/RSS 측정값이 아니며 문자열·dict 확장과 다른 상주 데이터까지 더해지는 위험 근거다. `docker-compose.app-only.yml`에는 `mem_limit: 768m`이 있다. 마운트가 불완전하거나 DB만 빠진 배포가 조건이며 실제 파일을 숨기거나 OOM을 유발하지 않았다.
- **고치는 방향:** 운영에서는 SQLite baseline을 필수 산출물로 지정하고 누락·스키마 불일치 시 명확히 기동 실패 처리한다. CSV 폴백은 메모리 여유가 있는 개발 환경의 명시적 선택으로 제한한다.
- **확신 정도:** 자동 폴백과 파일 크기는 **확인함**. 실제 OOM과 임계 RAM 사용량은 **추정**. 알려진 188MB CSV 워밍업 지연과는 다른 장애 조건이다.

## 13. 분석 초기화는 동기이며 한 번 실패하면 복구하지 않음

- **무엇이 문제인지:** 정상 기록은 큐에 넣지만 첫 `track()`는 요청 스레드에서 디렉터리 생성·SQLite 연결·WAL 설정·스키마 작성·commit을 먼저 수행한다. 잠금 대기/디스크 오류가 첫 사용자 요청에 영향을 주며, 초기화 실패 시 `_init_failed=True`가 워커 수명 동안 유지된다. 화면은 살아도 분석이 복구되지 않는 상태를 정상적인 0건과 구분하기 어렵다.
- **터지는 상황 / 근거:** `track():203` → `_ensure_started():129–135`, `_connect():113–116`의 5초 busy timeout. 초기화 예외는 `142–145`에서 플래그를 고정하며 `123–127`에서 이후 재시도를 막는다. writer의 배치 쓰기 오류(`173–178`)도 이벤트를 버리고 넘어간다. 첫 초기화 때 잠금 충돌·일시 권한/디스크 문제가 발생하면 이후 정상화돼도 그 워커는 기록을 재개하지 않는다. 홈의 인기 집계는 별도로 요청 중 동기 조회한다(`app.py:6301–6307`).
- **고치는 방향:** 요청 처리와 초기화 대기를 분리하고, 영구 비활성 대신 간격을 둔 제한적 재시도를 제공한다. 초기화 실패·큐 유실·writer 상태를 구분해 확인할 수 있도록 한다. 인기 집계 조회는 읽기 전용 연결을 사용하고, 실패와 실제 집계 0건을 구분한다.
- **확신 정도:** **확인함** — 동기 호출·실패 플래그·복구 부재 확인. 실제 DB 잠금/디스크 장애를 유발하는 시험은 하지 않음.

## 14. 버스 필터 전용 CSV 의존과 실패 캐시 고정

- **무엇이 문제인지:** 일반 버스 상세는 SQLite baseline을 쓰지만 버스 노선 필터용 `_bus_route_lookup()`은 `data/baseline/bus_baseline.csv`를 따로 읽는다. 파일 누락·중간 파싱 오류를 삼키고 그때까지 만든 빈/부분 결과를 장기 캐시한다. SQLite가 정상이어도 자동완성/탐색만 조용히 틀릴 수 있다.
- **터지는 상황 / 근거:** `app.py:7847–7866`의 직접 CSV 읽기와 `except Exception: pass`, 오류 여부와 무관한 `_EXPLORE_LOOKUP_CACHE["bus_routes"]` 저장. API `6964` → `_bus_routes_by_type()` → 해당 조회, Explore `8283`에서 사용한다. 캐시가 없는 각 워커의 첫 해당 요청은 약 **11,102,422 bytes** CSV를 파싱하고 노선 집합을 만든다. 파일을 나중에 복구해도 이미 만들어진 캐시는 재시작/명시적 삭제 전까지 재시도하지 않는다. 현재 파일은 존재한다.
- **고치는 방향:** 버스 노선 요약을 동일 버전 SQLite 또는 별도 작은 사전 산출물에서 가져온다. 정상 빈 결과·적재 실패·부분 결과를 구분하고 실패 결과는 완성된 장기 캐시로 게시하지 않는다.
- **확신 정도:** **확인함** — 파일 의존과 캐시 게시 흐름 확인. 실제 파일 누락 시험은 하지 않음.

## 16. 카카오 디스크 캐시의 비원자적 갱신

- **무엇이 문제인지:** 여러 워커가 공유하는 캐시 JSON을 임시 파일 없이 `open("w")`로 덮어쓴다. 다른 워커가 쓰는 중 읽으면 부분 JSON을 읽어 캐시 미스로 판단하고 외부 요청을 반복할 수 있다. 파일 확인과 `stat()` 사이의 삭제·교체도 예외 처리 범위 밖이다.
- **터지는 상황 / 근거:** `services/kakao_local_service.py:95–97`의 제자리 쓰기와 `78–81`의 파싱 실패 처리. `74,85`의 `path.stat()`는 try 밖에 있다. 같은 단지의 캐시 만료 직후 두 워커가 동시에 조회하거나 캐시 정리와 요청이 겹치는 상황이 조건이다. 기본 상세 경로의 카카오 호출은 꺼져 있으므로 상시 공개 경로의 장애라고 단정하지 않는다.
- **고치는 방향:** 워커별 임시 파일을 완성한 후 원자적으로 교체하고, 파일 조회 전체의 실패를 안전한 캐시 미스로 처리한다. 동일 키의 중복 갱신을 제어하거나 마지막 정상 캐시를 재사용한다.
- **확신 정도:** 쓰기·예외 처리 범위는 **확인함**. 실제 경합으로 손상 또는 500이 발생하는 빈도는 **추정**이며 파일 쓰기·삭제 시험은 하지 않음.

## 보안·캐시·동시성에서 확인한 범위

- **입력 전달:** Jinja의 일반 자동 이스케이프와 `tojson`을 사용하고, 확인한 baseline/격자/analytics SQL의 사용자 값은 placeholder로 바인딩한다. 동적 테이블·컬럼은 내부 설정에서 나온다. 상세 URL의 단지명으로 임의 파일을 여는 경로는 확인하지 못했으며 OG 파일명은 해시를 사용한다. 이것이 모든 XSS/SQL 공격에 대한 완전한 보안 검증을 의미하지는 않는다.
- **CDN:** `/apartments/...`, `/compare`, `/explore`, `/area`의 GET/HEAD 200에는 `public, max-age=300, s-maxage=86400`이 붙는다(`app.py:330–346,395–410`). 결과 차이는 주로 URL 파라미터이며 로그인/세션 쿠키에 따른 개인 응답은 확인하지 못했다. 따라서 서로 다른 이용자 응답이 섞인다고 단정하지 않는다. 실제 Cloudflare 캐시 키가 쿼리를 포함하는지는 서버/대시보드를 보지 않아 **미확인**이다. 관리자 응답에 위 public 헤더를 붙이지 않지만 명시적 no-store도 없다. 404/500에도 이 함수가 no-store를 직접 설정하지 않는다는 점은 주석의 ‘캐시 금지’와 구분해야 한다.
- **서비스 워커:** `static/sw.js`는 정적 자산 cache-first, 탐색 응답 network-first이며 전체 요청 URL을 키로 사용한다. 페이지 캐시 상한은 40개, 관리자/API/OG/Excel/healthz/robots/sitemap은 제외한다. 네트워크 예외 때만 저장된 HTML/오프라인 페이지로 폴백하고 HTTP 500 자체에는 폴백하지 않는다. 정적 캐시에는 별도 용량 상한이 없고 갱신은 URL 버전 또는 `CACHE_VERSION` 수동 증가에 의존한다. 이 검토에서 현재 잘못된 점수가 SW 때문에 재사용되는 사례는 확인하지 못했다.
- **프로세스 캐시:** baseline SQLite 연결은 PID를 확인해 fork 후 다시 열고(`services/preload_service.py:210–220`), 분석 writer는 워커에서 지연 시작한다. 기본 sync 워커 내부의 무잠금 dict를 곧바로 스레드 경쟁 문제로 보고하지 않았다. 공유 파일인 카카오 캐시의 경합은 #16과 별개다. 격자 무거운 연산은 Linux 파일 잠금과 제한된 캐시 크기를 사용한다.
- **데이터 갱신:** 점수·분포·Explore·거래 캐시 대부분은 프로세스 수명 단위이며 데이터 버전 감지는 없다. preload된 데이터는 워커만 교체하면 마스터의 이전 상태를 상속할 수 있으므로 데이터 교체 시 마스터/컨테이너 재시작이 경계다. 현재 배포 절차를 실행하거나 서버의 실제 재시작 방식을 확인하지 않았다.
- **기동 예열:** `gunicorn.conf.py:109–115`의 예산은 단계 사이에서만 확인하며, 진행 중인 단계에는 heartbeat를 계속 보낸다. 따라서 40초는 전체 기동 시간의 강제 상한이 아니다. 워커 예열을 실제로 실행하지 않았다.
- **알려진 기동 CSV 중복 읽기 개선 아이디어(1줄):** 필요한 열의 공통 조회 결과를 기동 단계에서 한 번 만들고 재사용하거나 작은 버전별 산출물로 분리하면 반복 파싱을 줄일 수 있다.

## 검증 결과와 실행 범위

- 서버·브라우저·외부 API에는 접속하지 않고 로컬 Flask test client로 확인했다. `load_dotenv`는 파일을 찾기 전에 메모리의 무동작 모듈로 대체했다. 카카오/국토부 API fallback·분석 이벤트 기록·rate limit을 검증 프로세스에서만 껐으며, 관리자 검증은 가짜 토큰으로 했다. 그러므로 실제 rate limit 횟수/서버 설정은 시험한 것이 아니다.
- 원본 코드 파일은 수정하지 않았다. 메모리에서만 함수 계수기·모의 응답·빈 baseline을 주입했고, 코드의 위험 분기별 확인 여부를 각 항목에 적었다. 격자 기동 warmup은 파일 잠금/부하를 피하려고 검증 프로세스에서만 건너뛰었다.
- 기존 테스트는 같은 제한을 둔 프로세스에서 `tests/test_correctness.py`를 대상으로 `not pure_kakao_cache` 조건, pytest cache/logging 플러그인과 캡처·assert 재작성 비활성화 후 실행했다. 결과는 **16 passed, 1 deselected (0.87s)**. 첫 시도는 pytest의 로그 파일 열기를 파일 쓰기 차단기가 막아 내부 오류였고, 플러그인을 끈 재실행이 통과했다.
- 전체 `python -m pytest -q tests`는 실행하지 않았다. 기존 카카오 캐시 테스트는 임시 JSON을 만들며, 홈 게시판/빌더/스카우트 테스트도 임시 파일·DB를 만들거나 빌더 CLI/산출물 생성을 검증한다. 보고서 한 파일만 생성하고 재빌드를 하지 말라는 제한 때문에 제외했다. 테스트 파일은 추가하지 않았다.
- 단일 로컬 요청 관찰값: `/result` 0.182초 / 364,304 bytes, 같은 단지 비교 `/compare` 0.053초 / 340,294 bytes, 조건 있는 `/explore` 0.021초 / 47,062 bytes, `/area` 첫 요청 0.438초·다음 요청 0.308초. 실행 순서에 따른 캐시 차이가 있고 압축 전 본문 크기다. 서버 성능 비교나 p95 지표로 사용할 수 없다. RSS/동시 부하/OOM은 측정하지 않았다.

### 검증 방식과 제약 준수 한계

**`data/analytics`가 전혀 바뀌지 않았다고 보증할 수 없다.** 분석 이벤트 쓰기를 비활성화하고 Python의 파일 쓰기·네트워크·`.env` 접근을 차단했지만, 홈의 `_directory_interest()`는 별도로 `analytics_service._read_connect()`를 호출한다. 이 함수는 읽기 전용 URI 없이 `sqlite3.connect(DB_PATH)`를 사용한다(`239–247`). SQLite 내부의 WAL/SHM 생성·제거 또는 연결 종료 체크포인트는 Python 파일 열기 차단만으로 통제되지 않을 수 있다. 이 점을 검증 후 확인하여 추가 DB 조회를 중단했다.

작업 폴더의 `data`는 원래 작업 폴더 데이터로 연결된 junction이었다. 확인 시 `analytics.db` 수정 시각은 2026-10-02 22:46:02 KST, analytics 디렉터리는 22:50:15 KST였고 남아 있는 파일은 `analytics.db` 하나였다. 검증 전 해시/시각을 수집하지 않아 이 변경 시각이 이번 조회 때문인지 다른 프로세스 때문인지, DB 내용에 변경이 있었는지 판정할 수 없다. 파일 삭제·복구·체크포인트를 추가 실행하지 않았다. 코드·기존 템플릿·커밋/브랜치/스테이징은 변경하지 않았고 Git 상태 목록에서 추가된 경로는 허용된 보고서뿐이었다.
